# Residual-factor basket execution review, before model definition

> This preserves the pre-estimation design discussion. The [approved fixed packet](../examples/residual_convergence/proposed_protocol.md) resolves its alternatives. The [final independent signoff](residual_convergence_preregistration_review.md) verifies the assembled implementation before fitting.

2026-10-06. Design review only: no historical estimation, signals, outcomes, numerical model runs or core changes. This is one proposed exploratory25th family, using the same fixed one-year window. It complements the [relative-value research memo](market_neutral_research_memo.md).

**Feasible with the current engine:** one centrally coordinated, multi-instrument perpetual account, using retained market GTC target attempts and actual reduce-only GTC cleanup. Orders are non-atomic, feedback arrives at completed-minute callbacks, and shared BTC/ETH hedge quantities net into one position per instrument. The execution protocol must disclose those facts before numerical research. It must not inherit eight independent-sleeve accounting from the previous outright candidates.

## Portfolio and native units

Use eight distinct native instrument IDs: BTC/ETH factor proxies and the six altcoins DOGE,1000PEPE,SOL,XRP,LINK,ADA. All share one USDT wallet and one actual Engine run. For signed altcoin dollar allocations a_i and frozen entry return-loadings beta_i,BTC and beta_i,ETH, illustrative hedge targets are:

`n_BTC = -sum(beta_i,BTC * a_i)` and `n_ETH = -sum(beta_i,ETH * a_i)`.

These are aggregated signed dollar amounts, not six duplicated factor accounts. Native quantity targets use only prices from the completed signal slice: `q_j = n_j / P_j`, rounded toward zero on that instrument's lot grid. No future opening price may enter sizing. Existing fills then pay their actual gapped/slipped opening prices. Gross sizing includes absolute alt notionals and absolute **net** BTC/ETH hedges, fees and prospective risk headroom. Recheck estimated factor exposure after rounding; if the prospective packet's minimum-notional or exposure admissibility tests fail, do not submit any part of the basket. This preflight cannot guarantee admission after a price gap.

PEPE's actual perpetual identity is **1000PEPEUSDT**, with price per bundle and native quantity per bundle; multiplier remains1. No spot conversion is needed for native perpetual dollar sizing. Percentage returns are invariant to the bundle scale. If a spot comparison is separately displayed, one perpetual unit corresponds to1,000 spot PEPE.

One position per instrument means the engine cannot preserve independent per-alt BTC/ETH hedge lots or isolated subaccounts for each conceptual residual trade. Average entry price, funding, collateral and closes apply to the net instrument position. Any allocation of shared hedge P&L back to altcoins is an explicitly defined analytical attribution, never another cash ledger or eight independent proofs. Losing hedge legs are economically expected; portfolio performance and economically justified prospective diversification tests replace an incoherent requirement that every hedge instrument profit.

## Prospective GTC transaction coordinator

The root design fixes one joint account, uniform8bps baseline/16bpsstress slippage, six altcoin gross budgets of `100000 * .25 / 6`, residual entry2/exit.5/stop4, maximum hold48hours and cooldown24hours. These are prospective instructions, not fitted findings from this review. Each entry's gross budget is normalized by `1 + abs(beta_BTC) + abs(beta_ETH)` before deriving alt and factor dollar allocations. Convert those allocations to rounded native quantities at that entry's completed prices; retain all three native contributions unchanged until that alt's declared exit. Aggregate BTC/ETH targets are the sums of active alt entries' **fixed native** contributions. Recomputing dollar hedge amounts at each new price would quietly introduce rebalancing.

A central transaction may change membership while other alt entries remain active. It freezes one full eight-instrument target vector and its pre-transaction actual quantities. It does not run independent alt controllers. During a transaction, new entry intents wait; the next transaction uses the then-current eligible intents, rather than replaying a queue of obsolete signals. Normal residual exits update the membership vector; a batch failure or liquidation instead flattens the entire actual account. Distinguish the model's per-alt24hour cooldown from the coordinator's global24hour failed-batch cooldown.

| State | Deterministic action at completed simultaneous minute slice |
|---|---|
| IDLE/HOLDING | If the eligible membership vector changes, preflight the complete rounded target packet. For each changed instrument submit its exact lot-rounded difference once as a market GTC order. Record generation, immutable targets, start quantities, IDs, returned Order references and activation boundaries; enter TRANSITION. |
| TRANSITION | Observe actual positions and existing order states each minute. Keep accepted/partial GTC orders pending; never cancel/reissue them simply because another minute passed. All targets reached within numeric tolerance and no live target orders implies completed transition. New entry signals do not mutate this transaction. A newly observed liquidation, invalid overshoot, rejected/cancelled order with an unmet target, declared risk exit during transition, or timeout invokes whole-account ABORT. |
| ABORT/FLATTEN | Cancel all tracked target/reversal orders before submitting cleanup. For each actual nonzero position without a live cleanup order submit one reduce-only market GTC close. Retain it through delayed activation and partial retries. Cancel an obsolete order once actual position is flat. Recreate a rejected/cancelled cleanup only on a later permitted callback if quantity is still executable. No new entry while any actual position or cleanup order remains. |
| FLAT/COOLDOWN | Account quantities must actually be zero and no tracked order live. A failed batch cannot re-enter before both this flat state and24hours after cleanup first reaches the genuinely flat state; a prolonged cleanup cannot consume the cooldown. Per-alt signal cooldowns remain independently applicable. |
| BLOCKED RESIDUAL | A subminimum quantity cannot be silently closed, dropped or treated as flat. Retain and mark it, continue to prohibit entries, and report the exact native dust plus reason. No artificial cash settlement. |

Target completion tolerance is `max(1e-9, lot_size * 1e-6)`, not one whole lot. Before declaring completion, cancel a live target order whose actual quantity already equals target; otherwise its future fill could overshoot. During TRANSITION, quantities must stay inside each instrument's pre-transaction-to-target interval within tolerance; a wrong-way movement or overshoot is an abort, not a new correcting reversal. A legitimate target reversal can monotonically pass through zero; actual engine closes and newly opened reserve remain separately accounted.

Preflight validates finite prices/loadings/quantities, native IDs, quantity grids, the normalized gross packet, all intended opening minimum quantities/notionals, fee and isolated-reserve headroom, and portfolio/instrument risk limits using completed observations. It cannot guarantee future gap-price admission. No invalid packet is partially submitted. An immediate submission rejection cancels already submitted sibling orders before the same-time open; a later risk cancellation aborts at the next observable callback. Once a declared transaction fails, retain no ad hoc smaller basket. Apply the same whole-account abort policy prospectively if an invalid requested packet is rejected before submission while prior holdings exist; it must not be conditionally chosen after outcomes.

### Rejection, dust and risk implementation details

Construct explicit `Order` objects rather than blindly calling `context.target` for every nonzero target. For delta opposite the actual position with `abs(delta) <= abs(position)`, set `reduce_only=True`, including a partial factor reduction toward a nonzero target. `context.target` only sets that flag for target zero; otherwise a small valid reducing hedge change can fail the minimum-notional test. Openings/reversals use ordinary market GTC orders. A reversal's **opening component** must pass the preflight opening minima; checking only the larger combined close-plus-open order can conceal an undersized newly opened hedge. Every difference must also pass minimum quantity and its lot grid.

Do not bypass engine admission. A conservative joint preflight checks all proposed opening reserve plus estimated transaction fees against currently available wallet cash, without spending anticipated releases or profits from a sibling close that might not execute first. Then check the proposed gross and per-instrument exposure at completed prices against the frozen configured limits. This is deliberately a current-observation estimate; gaps and sequential admission can still cause later cancellation and whole-account abort. Actual existing isolated collateral includes accumulated funding, not simply current marked notional divided by leverage.

Observe newly appended public `context.portfolio.events` from a saved cursor for `LIQUIDATION`, rather than relying only on current positions: a leg may already be flat after a forced fill. Preserve real liquidation fees and adverse prices, then cancel siblings at the next actual callback. Do not introduce an unannounced extra margin-ratio threshold beyond the root protocol's residual stop and the engine's existing margin rules. Local collateral/UPnL and modeled maintenance/close reserves should nevertheless be exported as diagnostics.

Use returned order IDs, retained public Order objects, `context.cancel`, `context.order`, actual `context.positions` and the public portfolio ledgers. Do not inspect future bars, overwrite positions/reserves or reach into private engine order dictionaries. A cleanup that remains executable can retry naturally as GTC; a subminimum quantity cannot. A below-minimum-notional close remains executable when reduce-only, but minimum quantity still binds. Record all such failures with transaction ID, actual/desired quantity, order status/reason and native grid. Never inflate an order to the next lot and reverse the position to dispose of dust.

**Deadline:** first eligible opening boundary after recorded activation plus5minutes. For a transaction submitted at T with zero delay, attempts at T,T+1,…,T+4 are visible at the T+5 completed callback; timeout there cancels before a sixth attempt. With one-minute delay, attempts T+1,…,T+5 are visible at T+6. An unresolved leg can therefore remain exposed for the full declared interval. Record that risk and the extra cleanup delay. An unexpected cancellation/rejection is observed failure immediately, rather than waiting the remaining timeout.

Terminal treatment must be chosen prospectively: schedule close attempts early enough for the declared delay, or preserve genuinely marked terminal positions with indicative exit reserve and an explicitly defined execution-validity gate. Forced synthetic terminal fills are forbidden.

### Timing that matters

The engine publishes the simultaneous close slice, settles actual funding and invokes `on_bars` before filling orders at the same timestamp's new open. Use `on_bars` as the single portfolio controller; individual `on_bar` callbacks must not submit competing basket orders. An order accepted at time T can fill at T's new open after the callback; actual feedback is visible at T+1minute's callback. Under a one-minute execution delay it first attempts at T+1minute's open, so entry assessment must wait until T+2minutes. Cancelling at T+1minute would cancel a stress order before its first attempt. For a non-grid latency, use the first minute-open boundary at or after the recorded `active_at`, then add one completed interval for feedback.

GTC orders attempt independently at eligible opens until completed or cancelled. Each leg can independently reject or partially fill; a single pending target is not a basket transaction. No `on_fill` callback exists: an unhedged leg can remain exposed until the next controller callback, and cleanup has its own delay. Funding and mark-based liquidation can occur in that interval. After one instrument liquidates, the engine cancels that instrument's orders, not all sibling hedge orders; sibling orders can still execute before the controller observes the failure. The cleanup protocol must record that exposure rather than claim instant basket cancellation.

## Engine limits requiring an explicit protocol choice

1. **Slippage is global per Engine.** `SimulationConfig.slippage_bps` applies to every instrument; native instrument metadata can vary fees but cannot specify per-instrument slippage. Existing single-sleeve BTC/ETH2bps,ordinary-alt5bps,DOGE/PEPE8bps assumptions therefore cannot be copied directly into one account. A prospectively declared uniform conservative8bps baseline/16bpsstress works without modifying core. It is a new disclosed assumption, not an unnoticed recreation of the earlier cost model. Supporting heterogeneous slippage instead needs a separately reviewed core change before freezing; no such change is proposed here. Under fixed slippage, default `spread_bps` is not additionally charged. Adverse tick rounding still applies.
2. **Sequential fills and risk admission.** Normalized bars are ordered by timestamp/instrument ID; opening fills process one instrument at a time. Submission ordering cannot make all legs atomic or change cross-instrument processing order. Admission reads actual current account state, and accepted orders reserve no cash in advance. Keep headroom for all intended legs and fees, but record any genuine gap-driven rejection. Per-leg FOK does not make a basket FOK.
3. **Isolated means per net instrument.** Hedge profits cannot automatically rescue an isolated losing altcoin or factor leg. Funding changes wallet cash and that instrument's reserve. The corrected proportional close semantics apply to all partial exits. Do not transfer reserve from another leg or net maintenance requirements analytically.
4. **Cleanup remains volume constrained.** Market GTC closes attempt at successive opens using prior completed volume and the configured participation cap. Reduce-only bypasses minimum notional for a close but not minimum quantity/lot requirements. Repeated cancel-and-replace can postpone activation forever under stress; retain existing valid cleanup orders. Actual liquidations are forced engine fills and bypass participation, an existing realism limitation that must remain visible.
5. **Minute realism boundary.** This engine has no historical quotes, depth, queue or intraminute mark path. Candle volume is an execution-capacity approximation. Do not add maker fills, guaranteed convergence fills, instantaneous hedge repair or atomic venue transactions to improve results.

## Synthetic tests required before historical launch

- Hand-calculated three-leg vector: signed alt allocation plus BTC/ETH factor hedges; exact rounded native targets, dollar gross, estimated beta exposure and fee/reserve requirements. Include1000PEPE and negative/zero beta coefficients.
- Two altcoin signals sharing the same factor: opposing hedge contributions net before ordering, without duplicated funding, positions or fees; simultaneous membership exit cannot leave stale shared hedge orders.
- GTC alt fills while factor has zero prior volume; factor fills while alt is rejected on minimum notional or risk admission; all legs partially fill even in matching proportions. Rejected cases abort on observable failure; insufficient-capacity cases retain orders until the five-minute activation-adjusted timeout, then abort the full actual basket with genuine entry and cleanup costs. Future candle volume changes cannot change opening capacity.
- Small shared hedge reductions to nonzero targets below opening minimum notional use reduce-only and remain valid; undersized reversal opening portions fail preflight.
- Baseline versus one-minute delay: assessment waits until after the actual eligible opening attempt. Repeated callbacks do not cancel pending delayed entry or cleanup before it has a chance to execute.
- Cleanup partial fills over multiple minutes, zero volume, minimum-quantity dust and final boundary; no reopening, accidental reversal, fictional flat state or manufactured terminal fill.
- Funding exactly at signal/activation/cleanup boundaries, with long and short native units; reserve and cash reconcile, retained funding is allocated proportionally on partial close.
- One leg liquidates before a sibling's delayed entry fills; controller cancels what it actually observes and flattens surviving/newly filled siblings on the next permissible callback. Genuine interim exposure and losses stay in ledgers.
- Signal vector changes while TRANSITION/ABORT: no second generation or direct `context.target` backlog. An abort requires full closure before fresh entries; normal membership changes remain one centrally serialized target transaction. Cash, marked equity, shared factor exposure and all event/order IDs reconcile.
- Deterministic identical-source replay and input-row permutation normalize to the same documented execution order; hash every code/data/protocol input and seal every execution export.

No historical numbers should launch until these synthetic timing/accounting checks and a fresh independent execution review pass. The existing one-year evidence remains reused exploratory history; a successful basket would not restore untouched evaluation or guarantee an enduring edge.
